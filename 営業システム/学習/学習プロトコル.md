# 学習プロトコル（データ → 改善 の更新ルール）

`集計.js` の出力を、具体的な基準・テンプレ変更に落とすルール。**これが学習アルゴリズム**。
更新サイクル：**10応募ごと、または週次**。

## 0. 記録（学習の燃料）
- すべての応募を `応募ログ.jsonl` に追記（応募時点で `outcome:"applied"`、`pred_win_rate` を必ず入れる）。
- 結果が出たら同じidの行を更新：`won/lost/no_reply/declined` ＋ 受注時は `actual_price/actual_hours/profit_rate/maintenance` と `win_factors`/`loss_factors`。
- **予測受注率(`pred_win_rate`)を必ず残す**。これが無いと精度を測れない。

## 1. キャリブレーション（01スコアの精度を上げる）
`集計.js` の「予測 vs 実績」を見る。
- ある優先度バンドで **|予測 − 実績| ≥ 15pt**（n≥3）→ `01-案件スコアリング基準.md` を調整：
  - 実績 < 予測（取れていない）→ 該当バンドの**閾値を引き上げる**（例：S=75→80）か、過大評価している配点（②③など）を下げる。
  - 実績 > 予測（取りこぼし）→ 閾値を下げる or 過小評価の配点を上げ、**応募範囲を広げる**。
- 変更したら理由を `インサイト.md` の「検証済み」に1行記録。

## 2. 提案文の淘汰と昇格（02の受注率を上げる）
- テンプレ別 受注率が **全体平均 −10pt 以下（n≥3）** → `02-提案文テンプレート.md` の該当テンプレを**リライト**。
- 受注案件の `win_factors` に繰り返し出る表現 → **「勝ち筋」として02に昇格**（例：「FVに具体的な予約導線」）。
- 失注の `loss_factors` の頻出パターン → 「失注の典型」として `インサイト.md` に記録し、次の提案で先回り対処。

## 3. ポートフォリオ配分（単価・利益率を上げる＝売上の主レバー）
- タイプ別に **期待値 = 受注率 × 平均利益率** を算出（`集計.js` が最稼ぎタイプを提示）。
- 期待値が高い順に**応募リソースを寄せる**。低い／赤字タイプは応募比率を下げる or 単価条件を上げる。
- 高単価型（プレミアム/システム/AI）が伸びるなら、量産LPの応募を削り**件数を絞って単価を取りに行く**。

## 4. 単価最適化（値上げ検証）
- あるタイプの受注率が**想定より高い（実績 > 予測 +15pt 等）** → 需要に対し安い可能性。次回から **提示額を1段上げる／上位プランを提案**してA/B検証。
- 受注率を見ながら、利益を最大化する価格帯を探る（受注率×単価が最大の点）。

## 5. 保守の付帯（MRR＝月商の安定化）
- 保守アタッチ率 < 50% → 全受注で保守プラン提案を徹底（`03` の想定質問にも回答済）。
- MRRの積み上げは「件数に依存しない売上」。月商100万の下支え。

## 変更の記録ルール
基準・テンプレを変えたら、必ず：
1. 何を・なぜ変えたか（根拠データ）を `インサイト.md` に1行。
2. コミットメッセージに反映（例：「学習: Sの閾値を75→80に（S実績が予測比-18pt）」）。

→ こうして**変更履歴がそのまま学習の軌跡**になり、後戻り・再現が可能になる。
