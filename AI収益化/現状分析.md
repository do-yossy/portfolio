## 2. 各機能の仕様（実装済みのもの）

### ① 買う前チェック

**入力**：品目（select・38件）／新品価格（number）／年間使用回数（1・3・8・24・150）／使用年数（1・3・5・10）／必要度（0・1・2）

**計算**（実装済み）
```js
uses      = freq × years                      // 通算使用回数
usedPrice = price × used                      // 中古購入価格
resale    = price × used × 0.6                // 想定売却価格
rentTotal = unit==="回" ? rent × uses
                        : rent × min(years×12, ceil(uses/2))
buyNet    = price − resale                    // 実質購入負担
usedNet   = usedPrice − (resale × 0.7)        // 実質中古負担
```
3案を `net` 昇順でソート → 最小が推奨。ただし `need===0 && uses<=3` なら **`stop`（見送る）**で上書き。

**出力**：判定バッジ／節約額／3案の比較表（支払額・実質負担・1回あたり）／根拠リスト／送客リンク／シェアテキスト

### ② 買わなくていい物レーダー

**入力**：年間使用回数（1・2・4・12）／使用年数（1・3・5）

**計算**（実装済み）
```js
bp        = ceil(buy / rent)     // 損益分岐の使用回数
rentTotal = rent × uses
diff      = buy − rentTotal      // 正ならレンタルが得
rentWins  = uses < bp
```
`diff` 降順でソート。28品目を横棒グラフで比較表示。

### ③ いまから何する？

**入力**：現在時刻／終了時刻（30分刻みselect）／予算（0〜99999）／人数（solo・multi）／気分（quiet・talk・any）／運動（rest・active・any）

**計算**（実装済み・本サービスの中核）
```js
startable  = now + 0.5                        // 移動30分を見込む
closeAdj   = close <= open ? close+24 : close // 日跨ぎ補正
latestStart= closeAdj − dur/60                // 最終入店可能時刻
fitsTime   = (dur + 30) <= freeMin
fitsOpen   = startable >= open && startable <= latestStart
```
除外条件を通ったものに**加点方式のスコアリング**（予算適合＋2／ソロ適性＋solo値／気分一致＋3〜4／運動一致＋2〜4／時間フィット＋2、不一致は減点）。

**出力**：条件サマリ／件数（要予約・予約不要の内訳）／上位10件のカード

### ④ 今日だけ安い

**入力**：予算／カテゴリ

**計算**：`now<=budget && (cat==='all'||cat===c)` でフィルタ → **割引率 `1−now/was` の降順**。`left<=2` を `urgent` として強調。

### ⑤ ソロマップ

**入力**：避けたいこと（talk・eye・book・none）／予算／滞在時間

**計算**（実装済み）
```js
w   = {talk:{q:3,s:1,n:1}, eye:{q:1,s:3,n:1}, book:{q:1,s:1,n:3}, none:{q:1,s:1,n:1}}[fear]
raw = quiet×w.q + solo×w.s + nobook×w.n
score = round(raw / (5×(w.q+w.s+w.n)) × 100)
```
**避けたいことによって重み付けが変わる**のが本機能の要点。

### ⑥ 無料品レーダー

**入力**：距離（0.5・1.5・3km）／運べる大きさ（1・2・3）／受取時期（today・week）

**計算**：3軸フィルタ → 距離昇順。徒歩分数は `dist/0.08`、自転車は `dist/0.25` で換算。

## 5. 問題点

### 5-1. 構造的な問題

| # | 問題 | 影響 |
|---:|---|---|
| **1** | **データがHTMLに直書き（28KB・160件）** | 1件直すのにHTMLを開く必要がある。**②と①でレンタル価格が二重管理**され、既にズレるリスクがある |

| **4** | サービス間の回遊がない | 6本が孤立。①で「レンタル推奨」と出ても②へ繋がらない |
| **5** | ユーザー設定が保存されない | 毎回エリアも予算も入れ直し |
| 6 | メディアクエリが③のみ | 他5本はスマホで崩れる可能性 |
| 7 | 計測タグなし | 離脱箇所が分からない |

### 5-2. 仕様上の要確認事項（**再構築前に決定が必要**）

指示いただいた計算式と、現在の実装に**差異があります**。勝手に変えず、ここで明示します。

| # | ご指示の式 | 現在の実装 | 差異 |
|---:|---|---|---|
| **A** | 実質購入負担 ＝ 新品価格 − 想定売却価格 | `price − resale` | **一致** |
| **B** | 実質中古負担 ＝ 中古価格 − 想定売却価格 | `usedPrice − (resale × 0.7)` | **不一致**。実装は売却額に0.7を掛けている（中古で買った物は売値がさらに落ちる想定） |
| **C** | レンタル総額 ＝ レンタル単価 × 使用回数 | `unit==="回"` なら一致。**`unit==="月"` は `rent × min(years×12, ceil(uses/2))`** | **月額品目（12件）は式が異なる**。ベビーカー・美容家電・電子ドラム等は「使用回数」ではなく「借りている月数」で課金されるため |
| **D** | 想定売却価格の算出 | `price × used × 0.6`（0.6が**ハードコード**） | ご指示のモデルには `estimatedResaleRate` フィールドがある。**データ側に持たせるべき** |

**判断をお願いしたい点**
- **B**：0.7を廃してご指示どおり単純化するか、`estimatedResaleRate` を「新品購入時」「中古購入時」で分けて持つか
- **C**：月額課金品目をどう扱うか（`rentalUnit` で分岐を残すのが実態に合う）
- **D**：0.6を `Product.estimatedResaleRate` として38品目分データに持たせる

## 7. 改修方針

### 7-1. 原則

1. **計算式は1文字も変えない。** 移設のみ。変更が必要な箇所（問題点5-2）は**事前に合意してから**着手する。
2. **データの値は変えない。** 160レコードをそのままJSON化する。
3. **リポジトリの方針（依存ゼロ・ビルドなし）を壊さない。** フレームワーク導入は**しない**。
4. **段階移行。** 各段階の終わりで6サービスが動く状態を保つ。

### 7-2. 段階

| Phase | 内容 | 完了条件 |
|---|---|---|
| **0（本書）** | 現状分析・仕様差異の洗い出し | **合意** |
| **1** | `data/` にJSON抽出。①②のProduct統合、③⑤のStore統合 | 既存6本がJSONを読んで**同じ結果を出す** |
| **2** | `lib/` に純関数を抽出（buy-check・break-even・time-calculation・deal-ranking・solo-score・distance） | **入出力が現行と完全一致**（回帰テストで確認） |
| **3** | `components/` と共通CSSを抽出 | 見た目が現行と同等 |
| **4** | `app/` にシェル（Header・BottomNavigation）を追加し、6入口を統合 | **1つのアプリとして回遊できる** |
| **5** | UserPreference（localStorage）／横断レコメンド | 条件が引き継がれる |

### 7-3. 技術選定

| 論点 | 判断 | 理由 |
|---|---|---|
| フレームワーク | **導入しない** | リポジトリ方針。現状も素のDOMで足りている |
| ビルド | **導入しない** | 1ファイル完結の慣習。ただし**共通CSS/JSは別ファイル化**して `<link>`/`<script src>` で読む形に緩和 |

| ルーティング | **静的HTML＋相対リンク** | SPAにしない。SEOの入口を増やす方針と整合 |

> **トレードオフの明示**：JSON外部化により「1ファイル完結」は崩れます。ただし `file://` で直接開けなくなる代わりに、**データの一元管理**と**重複の解消**を取ります。ローカル確認は簡易サーバー（`npx serve`）が必要になります。**この点は判断を仰ぎたい箇所です。**

## 10. 追加仕様と既存データのギャップ分析

ご指示いただいた仕様を、既存データと突き合わせました。**そのまま実装できるもの**と**データが足りないもの**を分けます。

### 10-1. まず件数の確認

ご指示の件数と実データにズレがあります（**データ整備で増やしたため**）。

| 機能 | ご指示 | 実データ | 備考 |
|---|---:|---:|---|
| ② 買わなくていい物 | 18品目 | **28品目** | 実勢価格の調査で10品目追加済み |
| ③ いまから何する | 28業態 | **47業態** | 食事・温浴・美容・運動を追加済み |

**多い分には問題ありません。** 全件そのまま移植します。

### 10-2. 計算式：既存と一致するもの（そのまま移植）

| 式 | 現在の実装 | 判定 |
|---|---|---|
| 実質購入負担 ＝ 新品価格 − 想定売却価格 | `price − resale` | **一致** |
| **1回あたり負担 ＝ 総コスト ÷ 使用回数** | `per: net/uses` | **一致**（比較表の「1回あたり」列で実装済み） |
| 損益分岐点 ＝ 購入価格 ÷ レンタル料金 | `Math.ceil(buy/rent)` | **一致** |
| 現在時刻＋移動時間＋所要時間 ≦ 閉店時刻 | `startable(now+0.5)` と `latestStart(close−dur)` の比較 | **一致**（式の形は違うが同値） |

> **③の補足**：現在の実装は「移動30分」を**固定値**にしています。ご指示の式に `移動時間` とあるので、**`UserPreference.transportation`（徒歩/自転車/バイク/車）から算出する変数に変える**のが自然です。⑥の移動手段登録と同じ仕組みを共有できます。

### 10-3. 新規仕様：データが不足しているもの ★要対応

#### ④ Deal Score（4要素の総合スコア）

```
DealScore = discountScore + urgencyScore + distanceScore + availabilityScore
```

| 要素 | 必要データ | 現状 |
|---|---|---|
| discountScore | `normalPrice` / `salePrice` | **あり**（`was`/`now`） |
| urgencyScore | `deadline` | **あり**（`close`） |
| availabilityScore | `remainingCount` | **あり**（`left`） |
| **distanceScore** | **店舗の緯度経度** | **無し** ★ |

→ **Deal に `storeId` を持たせ、Store 側に緯度経度を追加**しないと距離が計算できません。現在 `shop` は「洋菓子店」等の**文字列**で、実在店舗と紐づいていません。

#### ⑤ SOLO SCORE（5要素へ拡張）

```
SOLO SCORE = 一人入りやすさ + 会話不要度 + 予約不要度 + 初心者安心度 + 滞在自由度
```

| 要素 | 現在のフィールド | 状況 |
|---|---|---|
| 一人入りやすさ | ⑤ `solo`(1-5) / ③ `solo`(1-5) | **あり** |
| 会話不要度 | ⑤ `quiet`(1-5) | **あり**（③は `talk`(0-2) で**逆向き**。要変換） |
| 予約不要度 | ⑤ `nobook`(1-5) | **あり**（③は `book`(bool)。要変換） |
| **初心者安心度** | — | **全50件で未定義** ★ |
| **滞在自由度** | — | **全50件で未定義** ★ |

→ **50件すべてに2フィールドの付与が必要**です。判断基準の案：
- **初心者安心度**：初回でも迷わず利用できるか（券売機・料金が明瞭・手順が分かる）。例）映画館5／ボルダリング2（初回講習が要る）／立ち飲み2（作法が分かりにくい）
- **滞在自由度**：好きなだけ居られるか、追い出されないか。例）漫画喫茶5／図書館5／ラーメン店1（回転が速い）

**このデータは私が付与できます**が、主観が入るため**基準を先に合意したい**箇所です。

#### ⑥ 移動手段と持ち帰り可能性

| 必要データ | 現状 |
|---|---|
| ユーザーの移動手段（徒歩/自転車/バイク/軽自動車/普通車） | **無し** ★ → `UserPreference.transportation` |
| 商品の**重量推定** | **無し** ★（`size`(1-3) のみ） |
| 持ち帰り可能性（★評価） | **無し** ★（新規ロジック） |

→ `size` から重量を推定するルールが必要です。案：
| size | 想定 | 重量目安 | 徒歩 | 自転車 | バイク | 軽 | 普通車 |
|---|---|---:|---|---|---|---|---|
| 1 手で持てる | 〜3kg | 3kg | ★★★★★ | ★★★★★ | ★★★★☆ | ★★★★★ | ★★★★★ |
| 2 両手で運べる | 〜15kg | 15kg | ★★☆☆☆ | ★★★☆☆ | ★★☆☆☆ | ★★★★★ | ★★★★★ |
| 3 車が必要 | 15kg〜 | 30kg | ★☆☆☆☆ | ★☆☆☆☆ | ★☆☆☆☆ | ★★★★☆ | ★★★★★ |

**距離と組み合わせて減点**（例：徒歩でsize2かつ1.5km以上なら★1）。

#### 統合検索「何をすればいい？」★最も新規性が高い

```
入力：「3万円くらいでキャンプを始めたい」
出力：購入=寝袋 / レンタル=テント / 中古=チェア / 無料=クーラーボックス / 不要=○○
      推定節約額 18,000円
```

| 必要なもの | 現状 |
|---|---|
| **「活動 → 必要品目セット」の定義** | **無し** ★ |
| 各品目の購入/中古/レンタル価格 | **あり**（Product） |

| 自由入力の解釈 | **無し** ★ |

→ **新規エンティティ `ActivitySet` が必要**です。

```
ActivitySet {
  id, name,                    // "camping", "キャンプを始める"
  items: [
    { productId, priority, essential }   // 必須か・優先度
  ]

```

**キャンプ／釣り／登山／スキー／カメラ／DIY／ベビー用品** あたりを最初に定義すれば成立します。既存Productに該当品目が揃っているので、**セット定義を作るだけ**で動きます。

自由入力の解釈は、**まずキーワード辞書方式**（"キャンプ"→camping）で始めるのが現実的です。予算配分は「必須品目を優先し、予算内に収まるまで 購入→中古→レンタル→無料 の順に切り下げる」貪欲法で実装できます。

## 12. データ更新設計（Provider 抽象化）

ご指示の「将来的に外部データへ差し替えられる設計」は、**現状のコード構造と相性が良い**です。今は全データがHTML直書きですが、**読み出し口を1つに絞れば差し替えは容易**になります。

### 12-1. 構成

```
DataProvider（インターフェース）
      ↓
  ┌───┴────────────────────────────┐
StaticDataProvider   APIDataProvider   ScrapingDataProvider   PartnerDataProvider
（JSON同梱・今これ）   （REST/GraphQL）    （HTML取得・要注意）    （提携先フィード）
      ↓
ProductProvider / RentalProvider / StoreProvider / DealProvider / FreeItemProvider
      ↓
   lib/（計算ロジック）→ components/（描画）
```

### 12-2. インターフェース定義（JSDoc）

```js
/**
 * @typedef {Object} DataProvider
 * @property {() => Promise<Product[]>}  getProducts
 * @property {(productId:string) => Promise<Rental[]>} getRentals
 * @property {(opts?:{lat?:number,lng?:number,radiusKm?:number}) => Promise<Store[]>} getStores
 * @property {(opts?:{date?:string,area?:string}) => Promise<Deal[]>} getDeals
 * @property {(opts?:{lat?:number,lng?:number,radiusKm?:number}) => Promise<FreeItem[]>} getFreeItems
 * @property {() => {name:string, updatedAt:string, isLive:boolean}} meta
 */
```

**全て `Promise` を返す形にしておく**のが要点です。今は同期的にJSONを読むだけですが、この形にしておけばAPI差し替え時に**呼び出し側を一切変えずに済みます**。

### 12-3. 各Providerの位置づけと注意点

| Provider | 用途 | 実装時期 | 注意点 |
|---|---|---|---|
| **StaticDataProvider** | 同梱JSONを読む | **Phase 1（今）** | オフライン動作を維持できる唯一の形 |
| **APIDataProvider** | 自社APIまたは公開API | 将来 | **サーバーが必要**。現在はサーバーレス |
| **ScrapingDataProvider** | HTMLを取得して解析 | **要検討** | ★下記 |
| **PartnerDataProvider** | 提携先のフィード（CSV/JSON） | 将来 | 提携が前提。ASP経由の商品フィードが該当 |

> ### ★ ScrapingDataProvider についての警告
>
> **リポジトリの方針（`CLAUDE.md`）に「自動巡回・自動応募は規約違反のため実装しない」と明記されています。** また、レンタル各社・予約サイトの多くは**利用規約でスクレイピングを禁止**しています。
>
> **インターフェースとして定義しておくのは問題ありません**が、実装・稼働の前に**対象サイトごとの規約確認とrobots.txtの遵守が必須**です。無断のスクレイピングは、収益化以前に**サービス停止リスク**になります。
>
> **推奨**：`ScrapingDataProvider` は枠だけ用意し、実際のデータ取得は **PartnerDataProvider（ASPの商品フィード）** と **APIDataProvider（公開API）** を優先してください。国税庁法人番号APIのような**公式API**は規約上クリーンです。

### 12-4. データ鮮度の扱い

各Providerが `meta()` で更新日時を返す設計にすると、**画面に「データ更新：2026-08-26」と出せます**。現在は `source: '実測'|'推定'` で信頼度を出しているので、**この2つを組み合わせると情報の確からしさが伝わります**。

## 13. ユーザー設定（ローカル保存）

「最初から複雑な会員システムは作らない」というご判断に同意します。**localStorage で十分**です。

### 13-1. 保存項目と現在の入力元

| 保存項目 | 現在どこで入力しているか | 型 |
|---|---|---|
| 現在地 | **どこにも無し** ★新規 | `{lat, lng, areaName}` |
| 予算 | ③④⑤ で毎回入力 | `number` |
| 移動手段 | **どこにも無し** ★新規（③の移動30分固定・⑥の距離判定に必要） | `'walk'\|'bike'\|'moto'\|'kei'\|'car'` |
| 一人行動 preference | ③ `who` / ⑤ `fear==='eye'` | `1-5` |
| 会話 preference | ③ `mood` / ⑤ `fear==='talk'` | `1-5` |
| 予約 preference | ⑤ `fear==='book'` | `1-5` |
| 好きなカテゴリー | **どこにも無し** ★新規 | `string[]` |

### 13-2. 設計上の注意

| 論点 | 判断 |
|---|---|
| 保存キー | `lifechoice.preference.v1`（**バージョン付き**）。スキーマ変更時に安全に移行できる |
| 読み込み失敗 | プライベートブラウジング等で `localStorage` が例外を投げる環境がある。**try/catch で囲み、失敗時は既定値で動く**ようにする |
| 位置情報 | Geolocation API は **HTTPS必須＋ユーザー許可**。**許可されない前提**で、市区町村の手動選択も併設する |
| 個人情報 | 現在のプライバシーポリシー（`legal.html`）に「入力内容はブラウザ内で処理しサーバーに送信しない」と記載済み。**localStorage 保存はこの記述と矛盾しません** |

**効果**：6サービスすべての初期値が埋まるので、「別々のツール」から「1つのアプリ」に体感が変わります。**これが統合の最大のメリット**です。

### ★ 事項11について（最も注意が必要）
